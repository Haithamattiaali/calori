# contracts/ — the API contract of Sips & Bytes

`openapi.yaml` is the one HTTP contract between the iPhone app, the admin console and the server (model decision
A2: REST, versioned `/v1`, contract-first, OpenAPI **3.1.0**). It is written from `way/model.md` §3 (modules and
routes), `way/join.md` (paths, field names, error rules, through §22 / delta D6), `way/vocabulary.md` (D2–D6),
`way/events.md`, `way/seed.md` (every example) and FRD §17–§18. Where those files disagree with an older lens
line, they win and the contract follows them.

**Size on 2026-10-01:** 146 paths, 169 operations (78 for the eater app, 87 for staff, 4 in test builds only),
354 schemas.

## How the contract is used

1. **The server implements it.** Each module serves its own operations from `api/modules/<name>/routes.py`; the
   operation's `x-module` names the owner and its tag groups it. The shared Pydantic models in `api/contracts/`
   are generated from this file (model §3.1 rule 2), so the request and response shapes are never typed twice.
   FastAPI's own `/openapi.json` is compared with this file in CI: a route or field that exists in one and not the
   other fails the build.
2. **Contract tests run from both sides.**
   - *Server side:* **schemathesis** generates requests from `openapi.yaml` and runs them against the app on the
     Firestore emulator with the `FixtureAnalyzer` (A4, A11); every answer must match its declared status, schema
     and `x-error-codes`. **openapi-core** validates the request and the response of every story test (pytest) and
     of every test-build request, so a story that passes cannot pass on an undocumented shape.
   - *Client side:* the `SipsCore` API client is **generated by swift-openapi-generator** (1.13.1, A16) from this
     file. `swift test` decodes every example in this file through the generated types (a mock transport), and the
     outbox's recorded commands are validated against the request schemas with openapi-core. A field the client
     cannot decode, or a command the server would refuse, fails on Linux before any simulator run.
3. **Checks on the file itself** (run by `scripts/check.sh`, A22):
   - `openapi-spec-validator contracts/openapi.yaml` — the document is valid OpenAPI 3.1.
   - the consistency check: `Error.code` is exactly the vocabulary's list (D2 + D4); every name in `x-events` and
     `x-events-later` is in `way/events.md`; every `x-stories` id exists in `way/personas/`; every POST, PUT, PATCH
     and DELETE carries a required `command_id` (UUID) except the two that store nothing and the test controls;
     every route model §3.2 lists is present; every example validates against its schema.

## Conventions (the long form is `info.description` in the file)

- **Auth.** Eater: Firebase ID token as a bearer (`eaterBearer`); AI paths add a limited-use App Check token
  (`appCheck`, header `X-Firebase-AppCheck`). Staff: console session cookie `sb_staff_session` (`staffSession`)
  plus `X-CSRF-Token` (`csrf`) on every mutation. A staff identity on an eater path is 403 `FORBIDDEN` for every id
  (J33); another eater's id is 404 `NOT_FOUND` in a path and 422 `UNIT_NOT_FOUND` in a body (J34).
- **Numbers are strings.** Energy, mass, volume, nutrients and shares are `ExactNumber`: an exact decimal (`"62.5"`)
  or a reduced rational (`"187/3"`); money, `_pct` percentages and factors are `Decimal` strings (`credit_factor`
  `"0.5"` is a fraction, D6-A8). Nothing is rounded on the wire; a figure the product fixes for display is its own
  field (`intake_target_kcal_shown`, `Shares.shown`). Reason: JSON numbers become IEEE-754 doubles in Swift's
  `JSONDecoder` and Python's `json`, which cannot hold 0.1 or 187/3; the nutrition core works in `Fraction` and
  `Decimal` (A6) and the golden cases (NFR-01) must survive every hop. Unknown is `null`, never `"0"`.
- **Commands.** `command_id` (UUID) on every mutation; a resend returns the original answer (A5). Revision checks:
  `expected_entry_version` on Entry commands (FRD §18 "expected entry version", events.md), `expected_revision`
  (or `expected_version`, `based_on`) elsewhere; stale → 409 `STALE_REVISION` with `current_revision`. Consume is
  not checked against the Day revision (J114). Request bodies are closed (`additionalProperties: false`).
- **Errors.** One `Error` schema (`code`, `message`, `field?`, `current_revision?`, plus `reason`, `state`,
  `limit`, `resets_at`, `request_id` where the join asks for them). HTTP status per code as J38; 409
  `VALIDATION_ERROR` with `reason` for conflicts that have no code of their own (J35: `request_waiting`,
  `already_retried`, `plan_expired`, `privacy_review_not_signed`).
- **Extensions.** `x-module` (owner) · `x-events` (written in the operation's transaction, on success or refusal) ·
  `x-events-later` (written by a job or the clock for what the operation started) · `x-stories` · `x-error-codes`
  (by status) · `x-contract-added` · `x-build: test`. `access.refused` (any 403 `FORBIDDEN`) and
  `command.duplicate_ignored` (any repeated `command_id`) can follow any operation and are listed only where a story
  tests them.

## Versioning rule

The contract is `/v1`. `info.version` is `1.0.0-<date of the last delta>`.

- **A contract change is a dated delta with its impact**, written in `way/` like D4–D6 (date · name · reason ·
  impact on modules, the iOS client, the console and the stories or tests that read it) and applied to
  `openapi.yaml` in the same change, with `info.version` moved to the delta's date and a line added under
  "Changes" below. No change lands without its delta, and no delta lands without the file.
- **Additive** changes stay in `/v1`: a new operation, a new optional request field, a new response field, a new
  enum value in a response the client already treats as open.
- **Breaking** changes — removing or renaming a field, a new required request field, a tighter pattern, a changed
  status or error code, a new enum value in a request — need the delta to say how old clients keep working. A
  device can resend an old command at any time from its outbox or a restored backup (A5, E64), so the server keeps
  accepting every `/v1` command shape it ever published; a shape it cannot keep goes to `/v2` for that operation.
- The vocabulary owns the words: a new state, code, event or field word enters `way/vocabulary.md` or
  `way/events.md` by its own delta first, then this file.

## Module interfaces

The contract is the HTTP face of the 22 modules of `way/model.md` §3.2. Each module's Python interface
(`service.py`) is defined there, with what it owns, the events it emits and consumes, and its dependencies; the
rules between modules are §3.1, the hook protocols (`AccountDataOwner`, `SourceLinker`, `JobHandler`,
`GateProvider`, `RetentionParticipant`) §3.1, the pure `nutrition_core` package §3.3, the ports (`Analyzer`,
`JobQueue`, `MediaStore`, `TokenVerifier`, `FoodReleaseSource`, `ProcessorNotice`, `AppleSignInRevoker`) §3.4,
the console adapter §3.5 and the dependency graph §3.6.

## Routes this contract adds, and lines read through it

**Added** (`x-contract-added`: model §3.2 names the interface but no route; to be banked by a dated delta):
`POST /v1/units/name-match` (`analysis.unit_name_match`, J126 — a POST so typed words never sit in a URL) ·
`POST /v1/targets/suggestions/{id}/keep` (`targets.keep_target`, event `target.suggestion.kept`) ·
`POST /v1/meal-plans/{id}/reopen` (`plans.reopen`, J68 Undo → Saved). The D6 routes
`GET /v1/targets/activity-credit-offer` and `POST /v1/targets/activity-credit-offer/approve` come from J156.

**Lines read through the contract** (no source file was edited; these are for the session):
- Seed command fixtures `cmd_` + 4 hex are UUIDs on the wire; the loader maps `cmd_7a1e` to
  `00000000-0000-4000-8000-000000007a1e` (same for every `cmd_` fixture).
- Story values written as bare numbers (`credit_factor: 0.5`, `consumed_kcal 290`, `credit_cap_kcal: 300`) are the
  exact strings `"0.5"`, `"290"`, `"300"`. Older lens lines with `?day=` or `?date=` read `?diary_day_id=`.
- Grant lengths are ISO 8601 hours: `duration: "PT1H"` on a Grant, `durations` / `default_duration` on Grant
  settings (field names as admin-10.72 reads them; 1–24 h, D6-A1).
- `POST /v1/admin/wording` names the version in `text_version` (`c-ai-5`); `wording.published` calls it `key`.
  Wording state `proposed` (J153) has no route of its own in v1: the texts are supplied when publishing; a
  proposing route, if the console needs one over HTTP, is a delta.
- `GET /v1/reports/day` carries `consumed_kcal`, `target_kcal` and `remaining_kcal` at the top (the eater stories
  read them there) as well as the unrounded `totals`.
